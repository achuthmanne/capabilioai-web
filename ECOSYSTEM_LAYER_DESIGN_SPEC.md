# Ecosystem Layer — Design Spec

Sub-spec of `EXECUTIVE_PATH_DESIGN_SYSTEM.md` (Modules 10/11/12 — Communities, Events, Partner Hub — plus Marketplace, already listed as Module 12 in that doc, and Knowledge Center, a new addition). Sibling to `STARTUP_WORKSPACE_DESIGN_SPEC.md`, `FUNDING_HUB_DESIGN_SPEC.md`, and `EXECUTIVE_INTELLIGENCE_LAYER_DESIGN_SPEC.md` — inherits the same shell, tokens, and empty/loading/accessibility conventions from Startup Workspace §1.

Design-spec only, per explicit instruction — no frontend code in this pass.

## 0.1 Positioning

The Ecosystem Layer is where Executive Path stops being one founder's private workspace and becomes a place where founders, investors, universities, governments, and service providers actually transact with each other. The failure mode this brief is explicitly guarding against is turning that into a chat app, a Facebook Group, or a freelancer marketplace — the tell is the same as every prior spec: if a screen would feel at home in Discord or Upwork, redesign it. Density, curation, and AI-mediated relevance replace volume and browsing as the primary interaction model. A founder should never have to scroll a noisy group feed or browse forty freelancer profiles to find what they need — the system should surface the right community, event, partner, service, or resource proactively, the same way Opportunity Radar and AI Matchmaking already do in the Intelligence Layer.

Same visual system throughout: `#F59E0B` accent, DM Sans/DM Mono, hairline borders, restrained shadows, the DM Mono relevance/match-score convention from the Intelligence Layer spec reused here for Partner Match Scores and Marketplace provider recommendations, so a founder reads "score" the same way everywhere in the product.

## 0.2 Data reality check — read before implementing anything below

| Existing table | Reusable? |
|---|---|
| `org_events` | Real, and the schema already supports `type` values beyond `'post'` (used for institution posts) and `'general'` — an `'event'` type is unused today. Events module should extend this table (add `startup_id`/`is_public` scoping) rather than building a parallel events table. |
| `mentor_groups` / `mentor_group_members` | Real but tightly institution-scoped (`institution_id`, `mentor_user_id`, `student_id`) and currently referenced nowhere in the frontend — not a fit for Executive-path Communities as-is; a genuinely new `communities`/`community_members` pair is needed, though the moderator/member-role pattern from `mentor_groups` is worth reviewing before designing the new schema so the two don't diverge unnecessarily. |
| `org_opportunities` | Institution-scoped opportunity postings (title, company, role_type, eligibility, deadline) — flagged as a reuse candidate in both the Startup Workspace and Funding Hub specs already. Partner Hub in this spec is the most natural home for actually building on it, since "partnership opportunity" and "opportunity posting" are conceptually close — worth a single reconciliation pass across all three specs before choosing where this table's real home is, rather than three modules each assuming they get to claim it. |
| `studio_modules` | Real, generic content-module table (`skill_id`, `domain_key`, `type`, `content` jsonb, `ai_generated`, `generated_for_role`) currently powering Skill Studio learning content. Structurally very close to what Knowledge Center needs (playbooks/guides/templates as structured, AI-taggable content units) — strong reuse candidate over building a new content table from scratch, pending confirmation that its RLS/ownership model can extend to founder-authored or platform-authored business content rather than only skill-learning content. |
| `connections`, `follows`, `pulse_posts` | Same real infrastructure already established in the Intelligence Layer spec — Communities' Member Directory and Discussions should be thin layers over these rather than new social primitives. |

**Genuinely new tables needed:**

| New table | Purpose |
|---|---|
| `communities`, `community_members` | category (industry/stage/audience type), visibility (public/private/invite-only), moderator_ids |
| `community_posts` | Likely `pulse_posts` with a `community_id` column added, rather than a fourth parallel content table — same reuse principle as the Intelligence Layer's Executive Feed |
| `event_rsvps`, `event_attendance` | RSVP/ticketing/attendance tracking on top of the extended `org_events` |
| `partners`, `partnership_requests` | Partner directory + request/response workflow |
| `marketplace_providers`, `marketplace_services`, `marketplace_bookings`, `marketplace_reviews` | Service-provider directory, distinct entity model from `investors` (Funding Hub) even though the card patterns should look related |
| `knowledge_resources` | If `studio_modules` reuse isn't viable after review — playbooks/guides/case-studies as structured content, category-tagged (Fundraising/Legal/Finance/Sales/Marketing/Hiring/Leadership/Product/Technology/Compliance/Government Schemes) |

## 1. Communities

Two views: **Discover** (browse/search communities by the three organizing axes — Industry, Startup Stage, Audience Type — as filter chips, never a flat directory scroll) and **Community Home** (once joined). Community Home layout: header (name, category badges, member count, private/invite-only indicator), then a 2-column body — left is the primary content stream (Discussions, Pinned Posts pinned above the fold, AMA/Office Hours sessions shown as upcoming-event cards inline rather than a separate tab), right rail is structured intelligence (AI Summary of recent activity — "what happened this week," not a live unread-count badge; Trending Topics within this community specifically; Recommended Members to connect with; Suggested Discussions to start, generated from gaps in what's been discussed vs. what members have asked the AI assistant). Member Directory is its own tab, searchable/filterable, not a sidebar list. Moderator Dashboard (visible only to moderators) is a distinct, clearly-separated screen: pending-post queue, community analytics (real engagement numbers from `community_posts`/`pulse_posts` counters, never fabricated), member management.

## 2. Events

**Discover/Calendar view**: a real calendar (month/week/agenda toggle) plus category filter chips (Pitch Day, Demo Day, Investor Meet, Networking, Hackathon, Bootcamp, Webinar, Workshop, AMA, Founder Meetup, University Event, Government Program, Accelerator Cohort). **Event Detail** is a single scroll: Overview, Agenda (timeline component, not a table — matches the Startup Timeline visual language), Speakers (avatar row with role/bio on hover-or-tap), Sponsors (logo row, lighter treatment than speakers), Participants (avatar stack + count, full list behind a click), then a tab set for the in-event experience: Live Chat (only rendered during the live window, replaced by Q&A history afterward — never an always-empty chat box sitting idle for a webinar three weeks out), Networking (structured "who else is attending that matches your profile" list, reusing the Intelligence Layer's matchmaking card pattern rather than a freeform attendee wall), Questions, Polls. Post-event, the same screen transitions to show Recording, Resources, AI Notes (auto-generated from the recording/chat transcript, labeled AI-generated), Certificate (if applicable), Post-event Summary, AI Recommendations ("since you attended this, you might want..."). RSVP/Ticketing/Attendance and Calendar Integration are standard, unglamorous utility flows — no need to reinvent these, just make them fast (one-click RSVP, .ics export, no multi-step checkout for free events).

## 3. Partner Hub

**Discover**: filter rail by Partner Category (Technology, Enterprise, Cloud Providers, Channel Partners, Manufacturing, Distribution, Research Labs, Universities, Government, Media, International Expansion, System Integrators, OEM, Consulting) plus Region. **Partner Profile**: Overview, Capabilities, Industries, Regions (shown as a compact map chip or region-tag row, not a full interactive map — a full map is unnecessary weight for what's usually 2–3 regions), Partnership Models, Success Stories, Certifications, Case Studies, Services, Products, Contact Team, Mutual Connections, AI Match Score + Suggested Collaboration (same card language as Funding Hub's Investor Profile match scoring, for consistency across the whole Executive Path), Partnership Timeline (a simple stage tracker: Inquiry → In Discussion → Active → Concluded, distinct from Investor CRM's pipeline so partnerships and fundraising relationships are never visually confused with each other), Request Partnership (single clear CTA that opens a structured request form, not a generic "message" box).

## 4. Marketplace

Explicitly a curated service directory, not an open freelancer bidding marketplace — no reverse-auction/bid-war UI, no "lowest price wins" sorting as a default. Category rail (Legal, Finance, Accounting, Tax, Company Registration, Trademark, Patent Filing, Compliance, Fundraising Consultants, Fractional CXOs, Marketing, Branding, Design/UI-UX, Software Development, Product Strategy, Sales, HR/Recruitment, Cloud Credits, AI Tools, Productivity Tools, Cybersecurity, Training). **Provider Profile**: Profile, Portfolio, Pricing (packages shown as a clear 3-tier comparison card, Stripe-pricing-page style, not a wall of line items), Reviews/Ratings, Availability (real calendar-backed if possible, otherwise a simple "typically responds within X" statement rather than a fake live-availability indicator), Experience, Certifications, Case Studies. Actions: Book Consultation (calendar-integrated), Request Proposal (structured brief form), Favorites/Saved Services. **Compare Providers** is a dedicated side-by-side view (2–3 providers max, matching Stripe/Linear's restraint around comparison tables) rather than a checkbox-everything comparison grid. AI Recommendation surfaces 2–3 best-fit providers per category based on the founder's stage/industry/stated need, always with a one-line "why this one" rationale — never an unexplained ranked list.

## 5. Knowledge Center

Content-library screen, category-first (Playbooks, Templates, Guides, Case Studies, cross-tagged by domain: Fundraising, Legal, Finance, Sales, Marketing, Hiring, Leadership, Product Management, Technology, Compliance, Government Schemes — Startup India, MeitY, BIRAC named explicitly since these are real, specific Indian government program references worth surfacing accurately rather than generically — International Expansion, Taxation, Patents). Each resource card: title, format icon (playbook/template/guide/case study), read-time estimate, AI Summary (always visible without opening the full resource — respects the founder's time), Related Resources. Resource detail view has a persistent "Ask AI about this" affordance in a side panel, distinct from Universal Search — the AI here can generate a checklist or action plan grounded specifically in the open resource ("turn this fundraising playbook into a 30-day checklist for my stage"), not a generic chat.

## 6. Ecosystem integration — the founder journey, made visible

The brief's example journey (join a community → AI recommends a Demo Day → attend → meet an investor → investor requests a pitch → Pitch Room opens → Deal Room created → hire talent → grow) should not just be true in the data model — it should be visible to the founder as an actual on-screen artifact, not something that only shows up as disconnected notifications across five different modules. Recommended pattern: a persistent, collapsible **Journey Trail** component (available from the Executive Home Dashboard and from within any Ecosystem Layer screen) that renders as a short horizontal timeline of the founder's own real cross-module milestones — "Joined AI Founders community → RSVP'd to Demo Day → Connected with [Investor] → Pitch Room shared → Deal Room opened" — built from real timestamped events already being written across Communities, Events, the Intelligence Layer's connections, and Funding Hub, not a separately-authored marketing narrative. Each entry deep-links to where that step lives. This is the single most important integration-design decision in this spec: the "everything connects naturally" requirement is satisfied by making the connections legible after the fact, not by adding more cross-promotional widgets pushing the founder from module to module.

## 7. Implementation phasing (recommended order)

1. Events, built as an extension of the existing real `org_events` table (`type='event'`, add `startup_id`/`is_public`) plus new `event_rsvps` — lowest new-schema cost of the five modules, and immediately useful even with zero other Ecosystem Layer pieces built.
2. Knowledge Center — evaluate `studio_modules` reuse first (a short spike, not a full build) before committing to a new `knowledge_resources` table; whichever path, this has no dependency on any other unbuilt module.
3. Communities, with `community_posts` built as `pulse_posts` + `community_id` (same reuse principle as the Intelligence Layer's Executive Feed) rather than a new content table.
4. Journey Trail component — build this once Events + Communities are live, since it needs at least two real modules emitting timestamped events to be worth showing.
5. Partner Hub — depends on resolving the `org_opportunities` reuse question shared with Startup Workspace and Funding Hub; do that reconciliation before building `partners`/`partnership_requests`.
6. Marketplace — the most standalone-buildable of the five in terms of data model, but deliberately sequenced after the others since it's the module with the least natural pull-through from the rest of the Executive Path (a founder discovers Marketplace by need, not by an ecosystem journey funneling them there), so it benefits least from being built early.
7. Extend Journey Trail to include Partner Hub and Marketplace milestones, and reconcile with Funding Hub's own journey (pitch → deal room) once that module is live — at that point the full example journey in the brief becomes a real, traceable path rather than five separately-built features.
